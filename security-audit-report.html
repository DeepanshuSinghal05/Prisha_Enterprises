Executive Summary

This security audit identified critical Insecure Direct Object Reference (IDOR) vulnerabilities across the API endpoints that manage user-specific resources. The vulnerabilities allow authenticated users to access, modify, or delete data belonging to other users by manipulating resource identifiers in API requests.

Critical

Missing Authorization on Order Status Updates

Description

The updateOrderStatus endpoint in orderController.js does not verify that the order belongs to the authenticated user. Any authenticated user can modify the status of any order by knowing or guessing the order ID.

Affected Endpoint

  • PATCH /api/orders/:id/status

Vulnerable Code

// Line 161-168 in orderController.js const order = await Order.findByPk(id); if (!order) { return res.status(404).json({ success: false, message: 'Order not found' }); }

The code only checks if the order exists, but never verifies order.user_id === req.user.id.

Attack Scenario

1. Attacker creates an account and places an order (ID: 123) 2. Attacker enumerates order IDs (124, 125, 126...) 3. Attacker sends: PATCH /api/orders/125/status Body: {"order_status": "cancelled"} 4. Victim's order #125 is now cancelled by the attacker

Impact

An attacker can cancel other users' orders, change order statuses arbitrarily, disrupt business operations, and cause financial loss. This represents a complete breakdown of order integrity controls.

Required Fix

This endpoint should be restricted to admin users only. Regular users should not have the ability to update order status. The route in orderRoutes.js line 14 must be moved to admin routes with proper admin authentication.

High

Payment Verification Missing User Ownership Check

Description

The verifyPayment endpoint checks if an order belongs to the user (line 222 of cartController.js), but this check happens AFTER the payment signature verification. If the signature check fails, the error leaks information about whether the order exists, enabling order ID enumeration.

Affected Endpoint

  • POST /api/cart/checkout/verify-payment

Vulnerable Code

// Lines 201-228 in cartController.js const isSignatureValid = verifyPaymentSignature(...); if (!isSignatureValid) { await t.rollback(); return res.status(400).json({ success: false, message: 'Payment verification failed. Please try again.' }); } // Verify order belongs to user const order = await Order.findByPk(orderId, { transaction: t }); if (!order) { await t.rollback(); return res.status(404).json({ success: false, message: 'Order not found' }); } if (order.user_id !== userId) { // This check should happen FIRST await t.rollback(); return res.status(403).json({ success: false, message: 'Unauthorized to verify this payment' }); }

Attack Scenario

1. Attacker attempts payment verification with various order IDs 2. Different error messages reveal which orders exist 3. "Order not found" (404) vs "Unauthorized" (403) vs "Payment verification failed" (400) 4. Attacker maps out valid order IDs and their owners

Impact

Information disclosure through timing attacks and error message differences. Enables order ID enumeration which can be used in other attacks. While the ownership check exists, its placement after signature verification creates an information leak.

Recommended Fix

  • Verify order ownership BEFORE signature validation
  • Return identical error messages regardless of failure reason
  • Use constant-time comparison for all checks
High

Webhook Handler Lacks Order Ownership Verification

Description

The webhook handlers in paymentController.js (lines 70-151) update orders based on Razorpay events but never verify which user initiated the payment. A malicious actor could replay or forge webhook events to modify arbitrary orders if they bypass signature verification.

Affected Functions

  • handlePaymentAuthorized (line 63)
  • handlePaymentCaptured (line 79)
  • handlePaymentFailed (line 119)
  • handleOrderPaid (line 135)

Vulnerable Code

// Line 88-91 in paymentController.js const order = await Order.findOne({ where: { gateway_order_id: orderId } }, { transaction: t }); if (order) { // No user verification - blindly trusts webhook data await order.update({ payment_status: 'paid' }, { transaction: t }); }

Attack Scenario

1. If webhook signature verification is compromised 2. Attacker can send fake payment success events 3. Arbitrary orders marked as paid without actual payment 4. Goods shipped without payment received

Impact

While signature verification provides primary protection, defense-in-depth requires additional validation. If signature verification fails or is bypassed, there are no secondary controls. This could lead to unauthorized order completion and financial loss.

Recommended Fix

  • Add comprehensive webhook payload validation
  • Verify payment amount matches order amount
  • Check for duplicate payment IDs before processing
  • Log all webhook events with full payload for audit trail

Note

Recommendations

Immediate Actions Required

  • Remove user access to order status updates - Move PATCH /api/orders/:id/status to admin routes only
  • Reorder payment verification checks - Verify order ownership before signature validation in verifyPayment
  • Implement defense-in-depth for webhooks - Add payment amount validation and duplicate detection
  • Standardize error messages - Return identical messages for authentication failures to prevent enumeration
  • Add comprehensive logging - Log all authorization failures with request details for security monitoring

Long-term Security Improvements

  • Create a reusable authorization middleware that verifies resource ownership
  • Implement rate limiting on sensitive endpoints to prevent enumeration attacks
  • Add automated security tests that attempt IDOR attacks during CI/CD
  • Use UUIDs instead of sequential integers for resource IDs to increase attack difficulty
  • Implement comprehensive audit logging for all resource access attempts
  • Add monitoring alerts for suspicious access patterns (rapid ID enumeration, multiple 403s)

Compliance Impact

The identified IDOR vulnerabilities represent violations of:

  • OWASP Top 10 2021: A01:2021 – Broken Access Control
  • CWE-639: Authorization Bypass Through User-Controlled Key
  • PCI DSS Requirement 6.5.8 - Improper access control
  • GDPR Article 32 - Failure to ensure confidentiality and integrity of personal data

Fixing these vulnerabilities is critical for regulatory compliance and customer trust.

Conclusion

The API implements authentication correctly but has critical gaps in authorization. The address management endpoints demonstrate the correct pattern for verifying resource ownership and should serve as the model for fixing the vulnerable order and payment endpoints.

Priority should be given to removing the order status update capability from regular users and moving it to admin-only access. This single change eliminates the most critical vulnerability identified in this audit.
